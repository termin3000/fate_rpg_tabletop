## Production и Windows launcher (2026-10-17)

Актуальные пользовательские команды: npm run build (Next webpack + scripts/copy-standalone.js), Fate RPG.exe / start.bat / npm start. Подробнее [PRODUCTION.md](PRODUCTION.md). Старые записи о неработающей standalone-сборке ниже исторические и заменены этим разделом.

- copy-standalone.js компилирует оба однофайловых TypeScript-сервиса через установленный typescript.transpileModule, трассирует их и gateway/localtunnel через Next-версию nodeFileTrace, копирует зависимости, Prisma Client/native engine, static/public и Node runtime. Сборка не требует новых bundler-зависимостей. Rapier 0.15 при упаковке направляется на rapier.es.js, поскольку его .cjs.js неправильно помечен ESM для Node; игровая физика не изменялась.
- Geist 1.8.1 добавлен в зависимости; layout использует next/font/local вместо сетевого next/font/google. HTML lang=ru. npm run build успешно проходит без скачивания шрифтов.
- scripts/start-all.cjs — production supervisor: проверка свободных портов, абсолютный DATABASE_URL к исходным данным, запуск Node-процессов через runtime-entry.cjs с IPC, шлюз в supervisor, readiness, журнал logs/runtime.log, остановка owned services при выходе/сбое. FATE_DATA_ROOT указывает на исходную папку пользователя; API backups учитывают её. Никаких миграций/записи игровых данных при сборке нет.
- launcher/FateLauncher.cs компилируется в Fate RPG.exe через штатный Windows csc. Окно использует Windows Job Object с KILL_ON_JOB_CLOSE; запуск supervisor отложен до привязки к Job, что исключает ранних осиротевших детей. Режим --headless служит для тестов. Exe в корне использует .next/standalone/runtime/node.exe, поэтому системный Node/Bun для игры не нужен.
- ExitApplication в layout даёт локальному мастеру кнопку «Выход» с подтверждением. Gateway /_fate/control и /_fate/shutdown доступны только loopback + localhost Host без X-Forwarded-For; остановка требует случайный токен и точный Origin. Публичный localtunnel/LAN и UI игрока не получают управление. Закрытие вкладки не останавливает сервер; закрытие exe — останавливает.
- start.bat теперь production launcher; исходный bootstrap сохранён как start-legacy.bat. build.bat запускает npm run build.

## Временные HTTP 502 у игрока (2026-10-17)

Пользователь показал Next Console Error при назначении персонажа: apiGet → loadAdventures → applySnapshot, ответ 502 Bad Gateway. Само назначение передаётся отдельно; стек указывает на гидратацию приключения из сетевого снимка. Источник HTTP 502 (публичный localtunnel или локальный upstream) по одному скриншоту не установлен.

apiGet теперь повторяет безопасное чтение при HTTP 502/503/504 и сетевом TypeError: максимум три попытки с паузами 300/900 мс. Ошибки 4xx и разбора JSON не повторяются; POST/PUT/PATCH/DELETE не изменены, чтобы не создавать повторных записей. Ошибка GET теперь содержит путь API. applySnapshot не запрашивает список приключений повторно, если нужное уже известно; успешно гидратированное приключение без сцен больше не считается незагруженным при каждом снимке. После исчерпания повторов остаётся уведомление пользователю, диагностический вывод использует console.warn.

Пять тестов scripts/api-retry.test.ts проходят; eslint api.ts/use-network.ts проходит. Для этих проверок сервисы проекта не запускались — ранее данная просьба пользователя остановить процессы сохраняется. Исправление повышает устойчивость к кратковременным 502, но не устраняет постоянную недоступность сервера/туннеля.

Тест scripts/signaling-reconnect.test.cjs проходит против нового отдельного сервиса; действующий пользовательский сервис при проверке ещё демонстрировал старое поведение и требует перезапуска. Пользовательские процессы не останавливались.

Проверки: Bun-тест сохранения сессии; eslint изменённых TS/TSX; Chrome с двумя изолированными контекстами — вход игрока без reload мастера, принудительный reload мастера и игрока с восстановлением комнаты/публичного URL, явный выход. ## Назначение и заключение

Fate RPG Tool — русскоязычный виртуальный стол (VTT) для Fate Core / Fate Accelerated. Ведущий управляет приключением, сценами, картой и персонажами; игроки подключаются к комнате по коду или ссылке. Есть листы персонажей, аспекты, навыки, стресс и последствия, очки судьбы, инициатива, журнал бросков, заметки, предметы, генератор NPC, случайные таблицы и дополнительный модуль магии.

Карта поддерживает этажи, токены, зоны, рисунки, метки и туман войны. Броски включают обычные, встречные, массовые и синхронные; есть визуализация 2D/3D и бросок жестом перетаскивания.

Это полнофункциональное браузерное приложение с локальным сервером и Windows-оболочкой запуска. Архитектурно — Next.js-приложение с двумя вспомогательными сервисами. Код содержит много предметной логики и защит от прежних ошибок синхронизации. При этом крупные центральные модули, параллельные реализации сетевого слоя и неполная инфраструктура поставки затрудняют сопровождение. Наличие реализованных возможностей не означает, что их работоспособность подтверждена запуском.

## Потоки данных и архитектурные паттерны

### Клиент → хранилище → API → БД

Типовой путь: React-компонент → действие useFateStore → apiGet/apiPost/... → Next route handler → db (Prisma) → SQLite. Обратное преобразование готовит JSON для клиента. Это разделение по техническим слоям с отдельной папкой предметного UI. Строгой Clean Architecture, отдельного repository/service-слоя между API и Prisma здесь нет: обработчики напрямую обращаются к db.

Zustand сочетает состояние и команды над ним (Flux-подобный подход). Локальные открытия диалогов и мелкие состояния интерфейса часто остаются в useState. Вне React используется useFateStore.getState(). Общий store большой — около 206 КБ; map-panel.tsx около 89 КБ, physics-service/index.ts около 150 КБ на дату анализа. В этих модулях сосредоточено несколько обязанностей.

### Данные

Корневая сущность — Adventure. К ней относятся Character, Scene, LogEntry, Item, Folder, Note; связи с приключением используют onDelete: Cascade. ID в базе преимущественно cuid(), временные ID журнала начинаются с local_.

Сложные поля хранятся как JSON-текст в Prisma String: настройки приключения, навыки, аспекты, стресс, этажи, конфликт, результаты кубиков и т. п. В API используются JSON.stringify при записи и JSON.parse при чтении. Клиентские типы описывают уже разобранные объекты. Следствие: изменение структуры нужно согласовывать между types.ts, схемой, сериализацией API, store, импортом/экспортом и сетевыми сообщениями. Изменение только типа TypeScript не меняет существующие данные.

### Сеть

Фактически используемая компонентами реализация — src/hooks/use-network.ts. Топология звезды: ведущий — центральный узел, игроки соединяются с ним через WebRTC. Есть модульное общее состояние соединения: несколько вызовов хука должны использовать одну сеть. Используются heartbeat, переподключение, дедупликация событий и fallback через signaling.

Важное уточнение: buildSnapshot() в активном use-network.ts передаёт небольшой снимок — выбранное приключение/сцену, назначения персонажей и настройки. Полные игровые данные игрок загружает через REST API. Последующие изменения передаются событиями. Поэтому эта реализация предполагает доступ к общей серверной базе и не является полностью автономной репликацией между отдельными локальными установками.

src/lib/p2p/ содержит другую реализацию — P2PManager, WebRtcManager, SignalingClient, типы снимков и buildPlayerVisibleState(). По поиску ссылок getP2PManager() не вызывается UI; фильтр buildPlayerVisibleState() используется внутри этого отдельного менеджера. Не считать его автоматически действующим фильтром основного useNetwork.

Комментарии о signaling как сервисе «только SDP/ICE» неполны: сервер также обрабатывает state:sync и ретранслирует снимки. Актуальное поведение нужно сверять с обработчиками, а не только заголовками файлов.

В store регистрируются callback-функции вещания из сетевого хука — это ослабляет прямую зависимость store от сети. Флаги подавления повторной рассылки предотвращают циклы при применении удалённых изменений. Это паттерн callback injection и защита от эха событий.

### Кубики

roll-executor.ts — фасад, централизующий выбор способа броска. 3D идёт через очередь LiveRollEvent и отдельный физический сервис, результат возвращается асинхронно. Есть локальная 2D-физика и вычисление через performRoll как запасной путь. В 3D режиме сначала пробуют физику даже до установления соединения; доступность socket сама по себе не должна переключать новый бросок в 2D.

Для сетевого 3D-броска остальные клиенты подписываются на существующую физическую сессию; повторный запуск той же симуляции опасен. ID событий и сессий нужны для дедупликации. Цвета кубиков привязываются к инициатору, а не к наблюдателю.

В page.tsx намеренно монтируется только одна версия рабочего экрана — desktop ИЛИ mobile. Одновременное присутствие двух MapPanel/ServerDiceStage ранее вызывало двойные события броска. Сохранить это свойство при адаптации интерфейса.

### Offline и события

offline-sync.ts реализует optimistic update и локальную очередь отправки именно для журнала: запись немедленно появляется в Zustand, сохраняется в localStorage, затем отправляется на сервер; временная запись заменяется подтверждённой. После ошибок выполняются повторные попытки с задержками, после пяти неудач автоматические повторы прекращаются. Это не полная offline-first модель всех сущностей.

Модульные event bus на Set слушателей применяются для кратковременных событий жестов и удержания кубиков. Подписка возвращает функцию отписки. Долгоживущие данные хранятся в store, события жестов передаются отдельно. Регистры и singleton-подключения сокращают дублирование экземпляров, но требуют аккуратной очистки подписок и таймеров.

## Стиль и организация изменений

- Файлы преимущественно kebab-case, React-компоненты PascalCase, хуки useXxx; импорты через @/ → src/.
- Компоненты, использующие браузерные API и хуки, помечаются 'use client'. Серверный доступ к БД остаётся в API.
- Интерфейс преимущественно русский; комментарии смешанные, русские и английские. Читать текст в PowerShell с -Encoding utf8: без этого русские строки отображались некорректно.
- Для UI сначала искать существующий компонент в components/ui и аналогичный диалог в components/fate.
- Новую механику броска проводить через существующий исполнитель и очередь, учитывая локальный результат, журнал, визуализацию и передачу другим игрокам.
- Сохранять совместимость старых JSON-данных: значения по умолчанию и необязательные поля используются широко.
- Не редактировать prisma-client-backup как основной исходник; источник схемы — prisma/schema.prisma. После её изменения нужно отдельно проверить генерацию и portable-копию клиента.

## Запуск и проверки

| Процесс | Порт / команда |
| --- | --- |
| Next.js | 3000; bunx next dev -p 3000 (так запускает start.bat) |
| Signaling | 3004; в mini-services/signaling: bun run dev |
| 3D physics | 3006; в mini-services/physics-service: bun run dev |
| Caddy | 81; start-gateway.bat |

Caddy по умолчанию проксирует в 3000, а запросы с XTransformPort — на указанный локальный порт. Для сетевого доступа к вспомогательным сервисам нужно проверять именно используемый URL и конфигурацию шлюза/туннеля.

start.bat устанавливает Bun и зависимости, копирует Prisma Client из backup, при отсутствии базы вызывает prisma db push и запускает три процесса. При уже существующей db/custom.db шаг db push пропускается: launcher не гарантирует обновление схемы существующей базы.

Объявленные команды package.json:

- dev → bash scripts/dev-all.sh; check:physics/check:signaling → shell-скрипты из scripts.
- build → next build && node scripts/copy-standalone.js; start → node .next/standalone/server.js.
- dev:hot → next dev -p 3000 --webpack; lint → eslint .
- db:generate → prisma generate; db:push → prisma db push; db:migrate → prisma migrate dev.

В текущей поставке scripts отсутствует: dev, check:* и полный build зависят от недостающих файлов. Для production start сначала нужна успешно подготовленная standalone-сборка. Автоматические тесты и test script не обнаружены. Проверки не запускались: зависимостей нет, а задача касалась анализа и документации. После подготовки окружения полезны отдельный tsc --noEmit, lint и проверка основных сценариев вручную; успешная next build сама по себе не подтверждает корректность типов.

## Подтверждённые ограничения и точки внимания

1. next.config.ts включает typescript.ignoreBuildErrors: true и reactStrictMode: false. В tsconfig включён strict, но noImplicitAny: false; множество ESLint-правил отключено, mini-services исключены из lint. Типы и hooks не покрываются строгой проверкой сборки.
2. В прочитанных API нет проверки сессии/роли; GET characters возвращает персонажей приключения без фильтра hiddenFromPlayers. Права UI и отдельный неиспользуемый фильтр P2P не являются серверной защитой данных. Перед публикацией на недоверенную сеть нужен отдельный аудит API и управления туннелем/restore.
3. Caddyfile разрешает выбирать локальный upstream через XTransformPort. Учитывать это при оценке границы доступа шлюза.
4. snapshot API вызывает отсутствующий scripts/snapshot_backup.ts. Само наличие диалога резервных копий не гарантирует работоспособность создания снимков в этой поставке. Другие backup-операции требуют отдельной проверки.
5. Сгенерированный Prisma Client, существующая SQLite и schema.prisma могут расходиться; launcher при существующей БД это не исправляет автоматически.
6. Заголовочные комментарии местами описывают более ранний вариант реализации (сеть, 2D fallback). Проверять реальные вызовы и ветвления.
7. layout.tsx использует next/font/google: подготовка сборки может зависеть от получения шрифтов. В HTML lang="en", хотя основной интерфейс русский.
8. Не установлены фактическая работоспособность, производительность и устойчивость сетевой игры: это потребует запуска нескольких клиентов и сервисов.

## Что прочитать в следующей сессии

Сначала этот файл, затем только относящиеся к задаче исходники. Для изменения данных: types.ts → schema.prisma → нужный API route → store.ts → UI. Для сети: use-network.ts → signaling/index.ts → действия store. Для кубиков: roll-executor.ts → roll-stage-overlay / server-dice-stage → use-dice-physics.ts → physics-service/index.ts; для жестов дополнительно roll-gesture-provider и roll-gesture-bus.

После архитектурных изменений обновлять этот контекст, явно отделяя подтверждённые запуском результаты от выводов по чтению кода. Не записывать сюда секреты из .env, содержимое пользовательской базы и приватные данные игровых сессий.
